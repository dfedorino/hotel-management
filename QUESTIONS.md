# Вопросы, требующие решения

## 1. Где запускать Sonar?
Варианты:
- **SonarCloud** — бесплатно для публичного репозитория на GitHub, анализ в GitHub Actions. Нужны: публичный репозиторий, организация в SonarCloud и токен `SONAR_TOKEN` в секретах репозитория.
- **Локальный SonarQube в Docker** (`docker run -p 9000:9000 sonarqube:community`) — анализ командой `./mvnw sonar:sonar`, никаких внешних аккаунтов.

Пока по умолчанию: настрою `sonar-maven-plugin` и свойства проекта в `pom.xml` так, чтобы работали оба варианта, а в README опишу локальный запуск через Docker.

## 2. Добавлять ли PIT (мутационное тестирование)?
PIT вносит небольшие изменения в код («мутанты») и проверяет, что тесты их ловят — так видно, насколько тесты действительно проверяют логику, а не просто покрывают строки.
Минус — медленно (минуты на модуль), поэтому в обязательную сборку `verify` его включать не стоит.

Варианты:
- не добавлять;
- добавить отдельным профилем `./mvnw -Ppit verify` без порога (только отчёт);
- добавить профилем с порогом mutation score (например, 70%) и запускать в CI по расписанию.

Пока по умолчанию: не добавляю.

## 3. Уменьшать ли `times_booked` при снятии блокировки (`release`)?
`times_booked` растёт на 1 при успешном `confirm-availability`. Сейчас `release` (компенсация саги или отмена брони пользователем) уменьшает счётчик на 1 — то есть он считает только действующие бронирования, и номер после отмены снова становится «менее загруженным» в рекомендациях.

Альтернатива — никогда не уменьшать: тогда это счётчик всех когда-либо подтверждённых бронирований (включая отменённые), что ближе к «статистике», но после отмен рекомендации перекашиваются.

Пока по умолчанию: уменьшаю (не ниже 0), повторный `release` счётчик не трогает.

## 4. Как Booking Service авторизуется на внутренних эндпойнтах Hotel Service?
`confirm-availability` и `release` помечены в ТЗ как INTERNAL. Варианты:
- **сервисный токен**: Booking Service сам подписывает короткоживущий JWT (`sub=booking-service`, `roles=[INTERNAL]`) тем же HS256-секретом; Hotel Service пускает на эти эндпойнты только роль `INTERNAL`. Пользователь (даже ADMIN) вызвать их напрямую не может;
- **проброс пользовательского токена**: проще, но тогда любой USER с токеном может вызвать `confirm-availability` в обход саги, если доберётся до сервиса мимо Gateway.

Пока по умолчанию: сервисный токен с ролью `INTERNAL` (уже реализовано на стороне Hotel Service).
