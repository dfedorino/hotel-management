# ADR 0004. Идемпотентность и параллельные бронирования

## Контекст

Повторы и таймауты не должны создавать дубликаты и повторно менять доступность номера; параллельные
попытки занять один номер на пересекающиеся даты должны корректно получать отказ.

## Решение

- **Корреляционный идентификатор.** Клиент передаёт `requestId` (иначе он генерируется); в
  `bookings.request_id` уникальный индекс. Повтор запроса возвращает уже созданное бронирование без
  обращения к Hotel Service; одновременная доставка того же запроса упирается в уникальный индекс и
  возвращает победителя.
- **Ключ слота.** Hotel Service хранит блокировки в `room_reservations` с уникальным `request_id`:
  повторный `confirm-availability` возвращает сохранённый результат и не увеличивает `times_booked`
  повторно; `release` неизвестного или уже снятого слота — no-op.
- **Блокировка строки номера.** `confirm` и `release` берут `SELECT ... FOR UPDATE` на строку
  `rooms` (`PESSIMISTIC_WRITE`), поэтому проверка пересечения дат и вставка блокировки для одного
  номера выполняются строго по очереди: из параллельных запросов на пересекающиеся даты проходит
  ровно один, остальные получают 409.
- **Автоподбор под нагрузкой.** При `autoSelect` берутся до трёх наименее загруженных свободных
  номеров; если номер заняли между рекомендацией и подтверждением (409), бронирование переходит на
  следующий номер под ключом слота `requestId#2`, `requestId#3` (колонка
  `bookings.slot_request_id`), по которому затем работают компенсация и отмена.

## Последствия

- Тест `RoomAvailabilityServiceIntegrationTest.concurrentOverlappingConfirmsLetExactlyOneThrough` (8
  потоков, ровно одна блокировка).
- Нагрузочный тест Gatling: 40 пользователей одновременно бронируют одни даты — 0 ошибок, ни один
  номер не занят дважды, простаивает только номер на ремонте.
